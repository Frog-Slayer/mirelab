# 내 서재 블로그 개편 계획

내 서재(`/:studySlug/shelf`)를 개인 블로그로 다듬는다. 지금은 책장 하나뿐이라 "내가 읽은
것"은 있어도 "내가 쓴 글"이 없다 — 책에 매이지 않는 글(`Post`)을 추가하고, 그 글을 스터디
멤버가 읽을 수 있게 연다.

설계 전제는 `design.md` 를 따른다. 여기서는 그 위에 올리는 것만 적는다.

> **URL 축은 `/@username` 으로 정했다(1장).** 이 결정이 `User` 에 필드를 하나 늘리므로,
> 착수 순서의 맨 앞은 글이 아니라 그 필드다.

---

## 0. 정해진 것

| 축 | 결정 | 안 고른 것 |
| --- | --- | --- |
| 목록 화면 | `글` · `책장` 두 탭 병행 | 책장을 걷어내고 글 목록으로 교체 |
| 글의 단위 | 책에 매이지 않는 자유 포스트를 새로 만든다 | 기존 칸(한줄평·내 요약)을 글로 재조합 |
| 공개 범위 | 스터디 멤버에게 공개 | 나만 보기 / 로그인 없이 외부 공개 |
| 스터디 책 | 현행 유지 — 누르면 스터디 작품 상세로 | 서재 안에서 읽기 · 쓰기 |
| URL 축 | `/@username` 전역 경로. `User.username` 을 새로 만든다 | `/:studySlug/shelf/:userId` · `/@<uuid>` |

마지막 줄은 "쓰는 곳은 한 곳뿐"이라는 기존 결정(`ShelfService.getEntry` 주석)을 그대로
지킨다는 뜻이다. 서재 목록에는 스터디 책이 계속 꽂혀 있고, 누르면 스터디 쪽으로 간다.

### 무엇이 달라지나

|              | 지금                                          | 이후                                        |
| ------------ | --------------------------------------------- | ------------------------------------------- |
| 목록         | `ShelfPage` = 별점 히스토그램 + `Bookcase`     | `글` / `책장` 두 탭. 히스토그램은 책장 탭으로 |
| 글의 단위    | 없다 — 칸 값만 있다                            | `Post` — 새 엔티티                          |
| 공개         | 나만 (`/me/shelf`)                             | 내가 고른 스터디의 멤버에게                 |
| 본문 에디터  | `PersonalBlockNoteField` (개인 칸용)           | 그대로 재사용                               |

**글은 혼자 쓰는 것이라 `WorkBlock` 의 Yjs · 실시간 티켓 체계가 통째로 필요 없다.** 로컬
BlockNote + JSON 컬럼이면 끝이고, 이것 하나로 범위가 크게 줄어든다. 실시간은 공동 칸에만
붙인다는 `design.md` §5 의 선을 그대로 따른다.

## 1. URL 축 — `/@username`

지금 서재는 `/:studySlug/shelf` 다. `RootLayout` 에 이미 적어둔 대로 "개인 것이라 어느
스터디에서 열든 내용이 같고, slug 는 화면이 스터디 안에 있어서 붙을 뿐"이다.

**남의 서재를 볼 수 있게 되는 순간 이게 깨진다.** URL 에 "누구의"가 없으면 남의 블로그를
가리킬 방법이 없다. `design.md` §2-1 의 "사람과 멤버는 다르다 — `User` 가 `Study` 에
선행한다"를 따라 전역 경로로 간다.

```
/@yeongseo                내 블로그 (글 탭)
/@yeongseo/books          책장 탭
/@yeongseo/posts/:id      글 하나
```

`@` 접두어면 `RESERVED_SLUGS` 를 늘릴 필요가 없다 — 스터디 slug 에 `@` 가 못 들어가므로
구조적으로 안 부딪힌다.

### 1-1. `User.username` — 새 필드

지금 `User` 에는 URL 에 쓸 만한 게 없다. `name` 은 한글이고 중복될 수 있으며, `email` 은
남에게 보일 값이 아니다. 그래서 필드를 하나 추가한다.

```kotlin
@Column(unique = true)
var username: String,          // 소문자로만 저장 · 비교한다
```

**`name` 과 헷갈릴 수 있다는 걸 알고 고른 이름이다.** 그래서 둘의 차이를 여기 못박아 둔다.

| 필드       | 무엇                            | 예          | 바뀌나                    |
| ---------- | ------------------------------- | ----------- | ------------------------- |
| `name`     | 화면에 보이는 사람 이름          | `영서`      | 설정에서 언제든           |
| `username` | URL 에 쓰는 유일한 식별자        | `yeongseo`  | **안 바뀐다** (1-3)        |

형식은 `^[a-z0-9][a-z0-9_-]{2,29}$` 다. 대소문자를 섞어 받으면 `Yeongseo` 와 `yeongseo` 가
서로 다른 사람이 되어 URL 이 사람을 못 가리키므로, **받을 때 소문자로 내려 저장하고 중복
검사도 소문자로 한다.**

예약어도 막는다 — `me` · `admin` · `api` · `new` · `settings`. 특히 `/@me` 는 "내 블로그"
별칭으로 쓰고 싶어질 자리라 남에게 내주면 안 된다.

### 1-2. 어디서 받나

`User` 가 만들어지는 곳은 두 군데뿐이다.

- **`AccessRequestService.completeProfile`** — 승인받은 신청자가 이름 · 색을 정하는 화면.
  **여기에 username 입력을 추가한다.** 지금 이 함수가 `(requestId, email, name, color)` 를
  받으므로 인자 · 요청 본문 · 가입 화면(`SignupPage`)이 함께 바뀐다. 이미 쓰이는 username이면
  400 으로 돌려보내 다시 고르게 한다.
- **`AdminBootstrap.adoptOrCreate`** — admin 계정 보장. 사람이 입력할 자리가 없으니 설정값
  (`mirelab.admin-username`)으로 받거나 백필과 같은 규칙으로 만든다.

### 1-3. 기존 사용자 — 임의 백필 + admin 이 손으로 고친다

이미 가입한 사람들에게는 물어볼 기회가 없었다. 그래서 **부팅할 때 임의값으로 채운다.**

`ddl-auto=update` 가 기존 행이 있는 테이블에 `NOT NULL` 컬럼을 곧바로 추가하면 백필 러너가
실행되기 전에 부팅이 실패한다. 따라서 엔티티의 전환기 타입은 nullable 로 두고 컬럼을 먼저
추가한다. `AdminBootstrap` 다음 순서(`ORDER = 3`)의 호환성 러너가 `username` 이 비어 있는
행에 `user-<uuid 앞 8자>` 를 넣고, 충돌하면 UUID 조각을 한 글자씩 늘려 다시 시도한다. 백필이
끝난 운영 PostgreSQL에는 러너가 `NOT NULL` 제약을 건다.

임시값은 위 형식 규칙을 만족한다.
이렇게 하면 **URL 이 없는 사람이 한 명도 안 남는다** — `/@` 라우트가 언제나 성립한다는
뜻이라, 화면 쪽에 "아직 주소가 없는 사람" 분기를 만들 필요가 없다.

다만 `user-3f9a2c81` 을 평생 쓰게 할 수는 없다. 그 한 번의 교체는 **admin 이 DB 를 직접
고쳐서** 한다.

> **`username` 수정은 코드로 만들지 않는다.** 변경 API 도, 설정 화면의 수정란도 없다.
> 백필로 받은 임의값을 진짜 이름으로 바꾸는 일은 admin 이 `update users set username = ...`
> 로 한 번 처리한다.

지금 인원이 몇 명이고, 이 교체는 딱 한 번 있는 일이다. 여기에 "본인이 정했나" 같은 상태
필드를 두면 그 플래그가 영원히 남아서, 앞으로 가입하는 모든 사람이 쓰지도 않을 분기를 계속
들고 다니게 된다. **한 번뿐인 일에 영구적인 구조를 만들지 않는다.**

대가는 두 가지다. admin 이 손으로 넣는 값은 애플리케이션 검증(소문자 · 형식 · 예약어)을
거치지 않으므로 규칙을 admin 이 직접 지켜야 하고, 본인이 자기 주소를 고르려면 admin 에게
말해야 한다.

### 1-4. 옛 링크는 안 지킨다

admin 이 임의값을 진짜 이름으로 갈아끼우는 그 순간, 옛 `/@user-3f9a2c81` 링크는 죽는다.
지난 username 을 따로 저장해 리다이렉트하는 방법이 있지만, 임시값이 밖으로 공유됐을 리 없는
시점의 일회성 교체라 테이블을 하나 더 만들 값이 없다.

## 2. 백엔드

`ddl-auto=update` 라 마이그레이션 파일은 없다. 엔티티만 추가하면 스키마가 따라온다.

### 2-1. `domain/post/Post.kt`

```kotlin
Post(
  id: UUID,
  author: User,            // 서버가 토큰에서 정한다 — 남의 이름으로 못 쓴다
  title: String,
  bodyJson: String?,       // BlockNote 블록 JSON
  excerpt: String,         // 저장할 때 서버가 본문에서 뽑은 평문 200자
  work: Work?,             // nullable. 연결된 글은 그 작품 상세에도 함께 나온다
  published: Boolean,      // 지금 공개 상태인가
  publishedAt: Instant?,   // 처음 공개 상태로 저장된 시각. 다시 비공개로 돌려도 유지
  createdAt: Instant,
  updatedAt: Instant,
)
```

`bodyJson` 은 `SlotValue.value_json` 과 같은 이유로 `@JdbcTypeCode(LONGVARCHAR)` 다 —
BlockNote 문서는 블록마다 id · props · styles 가 붙어 금방 커져서 `VARCHAR(4000)` 에 안
들어가고, `@Lob` 을 쓰면 PostgreSQL 에서 문자열이라도 large object/OID 로 매핑돼버린다.

`excerpt` 를 서버가 뽑아 컬럼에 두는 이유: 목록 응답에 본문 JSON 을 통째로 실으면 글이
쌓일수록 목록이 무거워진다. **목록 응답에는 본문을 안 싣는다.**

`publishedAt` 은 현재 상태가 아니라 **최초 발행 시각**이다. 초안으로 처음 만들 때는 null이고,
`published = true` 로 저장되는 첫 순간에만 서버가 채운다. 그 뒤 비공개로 되돌려도 시각은
지우지 않고, 다시 공개해도 새 시각으로 덮지 않는다. 현재 공개 여부 판정은 반드시
`published` 로 한다.

### 2-2. `domain/post/PostShare.kt` — 공개 대상

`design.md` §2-1 의 `DiaryEntry.sharedStudyIds` 결정을 그대로 되살린다.

```
PostShare(post_id, study_id)      // 행이 없으면 = 나만
```

기존 `Visibility`(`ALWAYS` · `AFTER_DEADLINE` · `PRIVATE`)를 **재사용하지 않는다.** 글에는
마감이라는 개념이 없고, 공개 대상이 "어느 스터디냐"라서 값이 아니라 관계다.

### 2-3. `PostAccessChecker`

`WorkAccessChecker` 와 같은 자리 · 같은 이유다 — 판정이 두 군데로 갈리면 한쪽만 조여진다.
규칙은 하나다.

> 내 글이거나, `published == true` 이면서 그 글의 공유 스터디와 내 `myStudyIds` 가
> 하나라도 겹치면 볼 수 있다.

### 2-4. API

| 메서드 | 경로                          | 비고                                              |
| ------ | ----------------------------- | ------------------------------------------------- |
| GET    | `/api/me/posts`               | 초안 포함 전부. 본문 제외                          |
| POST   | `/api/me/posts`               | 초안으로 만든다                                    |
| GET    | `/api/posts/{id}`             | 본문 포함. 판정을 통과해야 한다                    |
| PATCH  | `/api/posts/{id}`             | 제목 · 본문 · 연결 작품 · 공개 대상 · 발행          |
| DELETE | `/api/posts/{id}`             | 작성자만                                           |
| GET    | `/api/users/{username}`       | 블로그 프로필 · 공개 글 수 · 공개 책 수            |
| GET    | `/api/users/{username}/posts` | 남의 블로그. 발행 + 공유된 것만                    |
| GET    | `/api/studies/{slug}/posts`   | 그 스터디에 공유된 현재 공개 글. 홈 캐러셀용        |
| GET    | `/api/users/{username}/shelf` | 책장 탭 — 현 `ShelfService.list` 를 열람자 기준으로 일반화 |
| GET    | `/api/works/{workId}/posts`   | 작품에 연결됐고 현재 열람자가 볼 수 있는 글 목록   |

**책장 API가 숨은 작업량이다.** 지금 `ShelfService.list(userId)` 는 "userId = 주인 =
열람자"를 전제로 값까지 그 사람 것만 골라온다. 남의 책장을 보려면 `list(ownerId, viewerId)`
로 갈라야 하고, 그때 **개인 칸의 `Visibility.PRIVATE`("내 메모")를 열람자 기준으로 걸러야
한다.** 안 하면 남의 비공개 메모가 새어 나간다.

남의 책장에서 책을 누를 수 있는지도 열람자 기준이다.

- 남의 책장에는 주인과 열람자가 함께 속한 스터디의 책 중, 주인이 평가 묶음(별점 + 한줄평)을
  `SlotValue.published = true` 로 공개한 책만 보여준다. 평가를 쓰지 않았거나 비공개로 둔 책,
  남의 개인 책, 열람자가 속하지 않은 스터디의 책은 제목도 노출하지 않는다.
- 따라서 남의 책장에 나온 책은 공개됐고 열람 가능한 책이며, 기존
  `/:studySlug/books/:workId` 로 링크한다. 본인은 개인 책도 기존 개인 책 상세로 들어간다.
- 작품 상세에서는 `Post.work` 가 그 작품을 가리키는 글 중 **`PostAccessChecker` 를 통과한
  글만** 보여준다. 발행 이력만 있다는 이유로 노출하지 않고, `published == true` 이면서
  그 글의 공유 스터디와 열람자의 스터디가 겹쳐야 한다. 작성자는 초안도 볼 수 있다.

`GET /api/works/{workId}/posts` 자체도 먼저 기존 작품 접근 권한을 확인한다. 작품을 볼 수 없는
사람이 연결 글 목록을 통해 제목이나 글의 존재를 알아내면 안 된다.

### 2-5. 테스트

`SlotVisibilityTest` 방식대로 — 한 문장이 곧 규칙 하나다.

- 초안은 남에게 안 보인다
- 공유하지 않은 스터디의 멤버에게 안 보인다
- 공유한 스터디의 멤버에게는 보인다
- 처음 공개할 때만 `publishedAt` 이 생기고 비공개로 돌려도 유지된다
- 남의 책장에서 `PRIVATE` 칸이 가려진다
- 남의 책장에는 함께 속한 스터디 책 중 평가를 공개한 책만 나오고 모두 작품 상세로 링크된다
- 작품에 연결된 공개 글은 공유 대상 멤버에게 보인다
- 작품에 연결됐어도 초안이거나 공유 대상이 아니면 글의 존재도 보이지 않는다
- 스터디 홈에는 그 스터디에 공유된 현재 공개 글만 나온다
- 작성자가 아니면 수정 · 삭제할 수 없다

## 3. 프론트엔드

### 3-1. 라우트

```
/@:username                  BlogPage        (글 탭)
/@:username/books            BlogPage        (책장 탭)
/@:username/posts/:id        PostPage
/@:username/posts/:id/edit   PostEditorPage  (본인만)
```

`/:studySlug/shelf` 는 내 블로그로 보내는 리다이렉트만 남긴다 — `UserMenu` 의 `shelfTo` 와
`ShelfWorkPage` 의 "← 내 서재" 링크가 이미 그 경로를 가리키고 있다.

블로그 화면은 `RootLayout` 안에 두되 `StudyNav` 는 안 뜬다. 지금 `StudyNav` 는
`current`(slug 매칭)가 있을 때만 그려지므로 자연히 사라진다 — **다만 그러면 스터디로 돌아갈
길이 헤더 전환기뿐이 된다.** 확인이 필요한 지점이다.

### 3-2. 화면

**`BlogPage`** — `GET /api/users/{username}` 로 읽은 프로필 머리(아바타 · 이름 · 현재 열람자가
볼 수 있는 글 수 · 책 수) 아래 탭 두 개. 본인 화면은 공개 여부와 관계없이 전체 개수를
보여준다.

- `글` 탭: 제목 · 발췌 · 날짜 · 초안/공개범위 배지. 시간 역순.
- `책장` 탭: 지금 `ShelfPage` 내용을 그대로 옮긴다 — `RatingHistogram` + `Bookcase`.
  - `Bookcase` 의 `onAdd` 는 본인이 볼 때만 넘긴다. 남의 책장에 "+" 가 뜨면 안 된다.
  - 남의 책장에는 함께 속한 스터디 책만 내려오므로 `entryHref` 는 모두 기존 작품 상세를
    가리킨다. 본인 책장의 개인 책만 기존 개인 책 상세로 간다.

**`WorkPage`** — 기존 작품 기록 아래에 `이 책에 연결된 글`을 둔다. 제목 · 발췌 · 작성자 ·
날짜를 보여주고 글 읽기 화면으로 연결한다. 서버가 현재 열람자에게 공개된 글만 내려주므로,
화면에서 별도의 공개 판정을 다시 만들지 않는다. 연결 글이 없으면 섹션 자체를 감춘다.

**스터디 홈** — 명예의 전당과 책장 사이에 `멤버들의 글` 캐러셀을 둔다. 해당 스터디에
공유됐고 현재 `published = true` 인 글을 최초 발행 시각 역순으로 카드에 담는다. 카드에는
작성자 · 제목 · 발췌 · 날짜 · 연결 작품을 보여주고, 트랙은 터치/트랙패드 가로 스크롤과 좌우
버튼을 모두 지원한다. 공개 글이 하나도 없으면 섹션 자체를 감춘다.

**`PostPage`** — 읽기 레이아웃. `RootLayout` 주석대로 글 읽는 화면은 줄이 길어지면 되레
읽기 힘드니 기본 기둥보다도 좁게 간다. BlockNote 를 `editable={false}` 로 그린다.

**`PostEditorPage`** — 제목 input + `PersonalBlockNoteField` + 연결 작품 선택(선택 사항) +
공개 대상 체크박스(내 스터디 목록) + 발행 버튼. 연결 작품은 내가 접근할 수 있는 스터디
작품과 내 개인 책에서만 고를 수 있고, 서버도 같은 권한을 검증한다. 자동 저장은
`PersonalBlockNoteField` 의 600ms 디바운스와 `useDebouncedSave` 패턴을 그대로 쓴다.
`design.md` §4 "속도가 곧 기능" — 제출 버튼을 기다리게 하지 않는다.

## 5. 짚어둘 점

**① 글 탭이 처음엔 비어 있다.** 기존 칸을 글로 재조합하지 않기로 했으므로, 그동안 쓴
한줄평 · 내 요약은 여전히 책 상세에만 있고 타임라인에 안 뜬다. 새 글은 책과 무관하게 쓸 수도
있고 `Post.work` 로 작품 하나에 연결할 수도 있다. 연결한 글은 블로그 글 목록과 그 작품 상세
양쪽에서 같은 글을 가리킨다.

**② 공개 대상이 글마다 다르다.** 스터디 A 에만 공유한 글과 아무 데도 공유 안 한 글이 한
목록에 섞이므로, 본인 화면에서 각 글의 공개 상태가 한눈에 보여야 한다. 안 보이면 "이거 걔가
봤나?" 를 매번 의심하게 된다.

**③ 이번 범위 밖** — 댓글, 새 글 알림(`NotificationsMenu` 가 껍데기만 있다), 스터디 통합
피드(`/:studySlug/feed`). 셋 다 `Post` 가 자리 잡은 뒤에 붙는 것들이다.
