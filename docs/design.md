# mirelab 설계 노트

스터디를 노션 대신 운영하기 위한 자체 서비스.

**지금은 독서 스터디(영서·호남·희남·승우)만 만든다.** 기록의 단위는 `작품`(책 한 권)이다 —
평점부터 요약·질문까지 전부 그 책 하나에 쌓인다. `모임`은 언제 만나는지만 아는 일정이고,
장 구분이나 순번은 두지 않는다. 내부 모델 이름은 `Session`으로 유지한다.

> **보류 중**
> 경제 스터디와 일기·피드는 한 번 만들었다가 걷어냈다. 머릿속 그림과 어긋나는 데가 많아서,
> 독서 쪽을 먼저 끝낸 뒤 다시 설계한다. 아래 §2-1 에 남긴 판단은 그때 참고용으로 둔다.
> 코드에서 지운 것: 일기·피드 화면과 데이터, 경제 스터디 시드, 멤버 헌주.
> 남긴 것: `User` / `Study` / `StudyMember` 구조 — 다시 만드는 비용이 크고 지금 방해가 안 된다.

## 1. 왜 만드는가

노션으로 운영 중이지만 세 가지가 구조적으로 안 된다.

### 뷰가 6종류로 고정

노션은 테이블·보드·갤러리·리스트·캘린더·타임라인 밖으로 못 나간다. 릴레이션과 롤업은 되지만, 원하는 모양으로 데이터를 재조합할 수 없다. **뷰를 코드로 짤 수 있다는 것**이 자체 개발의 유일하게 정당한 이유다.

에디터 성능이나 UI 완성도로는 노션을 못 이긴다. 이기려 들면 진다.

### 글과 데이터가 분리돼 있다

노션에는 세계가 둘이다.

- **블록** — 페이지 본문. 자유롭지만 그냥 텍스트
- **DB 속성** — 표의 열. 계산·정렬은 되지만 페이지 안에서 자연스럽게 못 씀

별점이 대표적이다. 감상문 안에 `★★★★☆`라고 쓰면서 동시에 평균 별점도 뽑고 싶은데, 노션은 이 둘을 잇지 못한다. **같은 값을 두 군데 쓰고 고칠 때도 두 군데 고친다.** 지금은 템플릿으로 때우고 있다.

→ 자체 개발하면 이 구분 자체가 없다. 화면에서 별 4개를 누르면 그게 곧 DB 값이다.

### 같은 내용을 세 번 쓴다

멤버들의 실제 사용 패턴:

```
① 개인 노션에 정리
      ↓ 복붙
② 공용 페이지에 옮겨 씀
      ↓ 모임에서 다듬어짐
      ↓ 복붙
③ 다시 개인 노션으로
```

게을러서가 아니라 **개인 공간과 공용 공간이 다른 페이지**라 생기는 왕복이다. 스터디 페이지는 모임별로 흩어지니 "내 관점에서 이어지는 기록"이 거기서 안 나오고, 그래서 자기 것을 따로 갖고 싶어 한다.

→ 한 번만 쓰고, 개인 뷰와 공용 뷰가 **같은 데이터를 다르게 모으게** 한다.

## 2. 핵심 개념: 칸(Slot)

콘텐츠를 페이지가 아니라 **이름 있는 칸** 단위로 저장한다. 각 칸은 무슨 값인지 시스템이 안다.
사용자 화면에서는 `내 요약`, `질문 · 토론거리`처럼 실제 이름을 우선 보여주고, `칸`이라는
시스템 용어는 설정에서만 쓴다.

칸에는 축이 넷 있다.

| 축       | 값                                        | 의미                                  |
| -------- | ----------------------------------------- | ------------------------------------- |
| **타입** | 별점 · 짧은 글 · 긴 글 · 목록 · 항목 목록 | 어떤 UI로 그리고 어떻게 저장하나      |
| **범위** | 개인별 · 공동                             | 사람마다 하나씩인가, 모임에 하나인가  |
| **공개** | 항상 · 마감 후 · 계속 비공개              | 언제부터 남에게 보이나                |
| **반복** | 스터디 · 모임                             | 모든 모임에 나오나, 이번 모임만인가   |

### 값은 전부 작품(책) 하나에 붙는다, 모임은 일정만 안다

처음엔 칸마다 "작품에 한 번 쓰나, 읽은 범위마다 쓰나"를 고르는 **대상** 축을 두고, 장
구분("4~6장")과 순번으로 모임을 구분했다. 써보니 한 권을 여러 모임에 걸쳐 읽을 때
줄거리·요약·질문 같은 칸이 모임 수만큼 흩어져, 책 하나의 기록인데도 다시 모아 봐야 했다.

**칸은 전부 작품 화면 하나에서만 쓰고 보여준다. 대상 축 자체를 없앴다.** `SlotValue.targetId`
는 항상 작품(Work) id 다. 모임(`Session`)은 장 구분·순번을 갖지 않고 **언제 만나는지**만
안다 — 모임 화면은 일정과 제출 현황을 확인하는 곳이고, 실제로 쓰는 곳은 작품 상세 하나뿐이다.

### 반복 = 콜아웃의 일반화

지금 노션에서 필요할 때 콜아웃을 붙이는 행위가 **특정 모임 즈음에만 작품 화면에 나오는
칸**이다(`SlotOwner.SESSION` + 그 칸에 연결된 모임 id). 별도 개념이 필요 없고, 몇 번 써보고
좋으면 스터디 기본 항목으로 올려 늘 보이게 할 수 있다. 값은 다른 칸과 마찬가지로 작품에
붙는다 — 달라지는 건 그 칸이 작품 화면에 지금 보이느냐뿐이고, 그 판단은 연결된 모임이 이
작품 소관인지로 정한다.

### 공개 = 개인 정리를 앱 안으로 흡수하는 장치

멤버들이 개인 정리를 이 앱 안에서 하고 싶어 한다. 그러려면 두 가지가 필요하다.

- **비공개 초안** — 마감 전엔 내 칸이 나만 보인다. 개인 노션에 먼저 쓸 이유가 사라진다 (①번 복붙 제거)
- **계속 비공개인 칸** — 공용에 안 올릴 잡생각을 담는 곳. 이게 없으면 결국 개인 노션을 계속 쓴다

### 공동 칸 = 항목 목록 + 메모

공동 문서와 개인 관점은 성격이 다르다. 한 텍스트에 섞으면 공동 문서는 누구 말인지 모를 잡탕이 되고, 개인 생각은 눈치 보느라 안 써진다.

그래서 **공동 칸은 항목 목록으로 통일**하고, 각 항목에 개인 메모를 붙인다.

```
줄거리 (공동)
  1. 농업혁명은 생산량을 늘렸지만 개인의 삶은 오히려 나빠졌다
       💬 지현   인구압 얘기랑 순환논증 아닌가?
       💬 준영   4장에 반박 나옴
  2. 화폐는 상호 신뢰의 시스템으로 작동한다
       🔒 나     실무랑 연결해서 생각해볼 것
```

메모는 **그 자리에 남으면서 내 기록에도 인용과 함께 쌓인다.** 따로 담아올 필요가 없다 (③번 복붙 제거).

> 공동 칸의 타입을 항목 목록 하나로 고정한 이유: 메모가 붙는 단위가 일관돼야 한다. 어떤 칸은 항목이고 어떤 칸은 흐르는 글이면 앵커가 두 종류가 된다. 긴 글이 필요하면 항목 하나를 길게 쓴다.

### 독서 스터디 초기 칸 구성

| 이름             | 타입      | 범위   | 공개           |
| ---------------- | --------- | ------ | -------------- |
| 평점             | 별점      | 개인별 | 항상           |
| 한줄평           | 짧은 글   | 개인별 | 항상           |
| 인상깊은 장면    | 목록      | 개인별 | 마감 후        |
| 내 메모          | 긴 글     | 개인별 | 🔒 계속 비공개 |
| 줄거리           | 항목 목록 | 공동   | 메모 허용      |
| 오늘 나온 이야기 | 항목 목록 | 공동   | 메모 허용      |

## 2-1. 스터디가 여럿이라 생기는 것

### 사람과 멤버는 다르다

영서·호남은 두 스터디에 다 있다. 멤버를 스터디에 묶어두면 한 사람이 멤버 두 개가 되고,
일기처럼 전역인 것에서 "누구 것인지"가 꼬인다.

```
User          영서 · 호남 · 희남 · 승우 · 헌주      ← 사람. 로그인 단위
  └ StudyMember ─┬─ 독서 스터디
                 └─ 경제 스터디
```

`SlotValue`, `Memo` 는 모두 `userId` 를 갖는다.

`StudyMember`는 화면 필터가 아니라 접근 권한의 경계이기도 하다. 스터디 URL 하위 화면과
스터디·작품·일정·칸 값·공동 기록 API는 모두 이 멤버십이 있어야 접근할 수 있다. 내 서재는
개인 API지만, 스터디 작품을 읽거나 기록할 때는 똑같이 해당 스터디 멤버십을 확인한다.

### 스터디마다 화면이 다르다

차이는 인원이 아니라 **작품을 다루는가**다. `Study.hasWorks` 하나로 갈린다.

|               | 첫 화면(탭 이름 `홈`) | 있는 탭 |
| ------------- | ---------------------- | ------- |
| 작품 O (독서) | 명예의 전당 + 책장      | + 모임  |
| 작품 X (경제) | 다음 모임               | 작품 없음 |

독서 스터디는 명예의 전당을 첫 화면(`홈`)으로 쓴다. 다음 모임은 상단 배너에서 바로 들어간다.
후보·읽는 중까지 포함한 전체 작품은 그 아래 책장 섹션에 있다 — 별도 `작품` 탭을 두지 않고
한 화면에 합쳐, 완료작 순위와 전체 책장을 오가며 보게 한다.

**경제 스터디는 코드를 고치지 않고 만들어졌다.** 칸을 화면에서 정의하니 별점 칸을 안 만들면
그만이다. 실제 구성:

```
이번 주 이슈   항목 목록 · 공동 · 메모 허용
용어           항목 목록 · 공동 · 메모 허용     ← 계속 재등장하는 것
내 해석        긴 글   · 개인별 · 마감 후 공개
관련 기사      목록    · 개인별 · 항상 공개
메모           긴 글   · 개인별 · 🔒 비공개
```

### 일기는 개인 것, 피드는 스터디 것

일기는 스터디에 속하지 않는다. 쓸 때 올릴 스터디를 고르면 그 피드에만 뜨고,
아무것도 안 고르면 나만 본다. 두 스터디에 동시에 올릴 수도 있다.

```
DiaryEntry.sharedStudyIds = []            → 나만
                          = ['st1']       → 독서 피드에만
                          = ['st1','st2'] → 둘 다
```

### 일정 화면은 두지 않는다

모임의 `meetAt`은 홈과 모임 기록 안에서만 보여준다. 독립 달력, 휴회·뒤풀이 일정, 날짜 조율은
핵심 작성 흐름이 자리 잡을 때까지 보류한다.

### URL 에 스터디를 넣는다

```
/reading        /reading/sessions
```

전환기 상태로만 들고 있으면 링크 공유가 안 된다.

`/s/` 같은 접두어는 쓰지 않는다. React Router 는 정적 세그먼트를 동적보다 먼저 매칭하므로
`/settings` 같은 전역 경로를 나중에 추가해도 `/:studySlug` 와 부딪히지 않는다.
진짜 위험은 스터디 slug 가 하필 예약어와 같을 때뿐이라, `RESERVED_SLUGS` 로 막는다.

## 3. 데이터 모델

```
Study ─┬─ Member
       ├─ SlotDef
       ├─ Work ───────────┬─ SlotValue  (작품, 칸, 작성자, 값)
       │                  └─ Memo       (작품, 칸, 항목ID, 작성자, 공개여부)
       └─ Session            모임 시각만 안다 — 일정 전용, 장 구분·순번·칸 값을 갖지 않는다
```

### SlotValue.value 는 JSONB

칸 타입이 사용자 마음대로 늘어나니 컬럼을 미리 못 만든다.

```jsonc
{"n": 4}                                    // 별점
{"text": "후반부가 늘어지지만…"}             // 짧은 글 / 긴 글
{"items": ["밀을 길들이지…", "화폐는…"]}     // 목록
{"yjs": "<binary>"}                          // 공동 항목 목록
```

평점 통계는 그냥 집계한다. 두 번 쓸 일이 없다.

```sql
select avg((value->>'n')::numeric)
from slot_value where slot_def_id = ?
```

### 공동 칸의 소유권 분리

- **항목 본문** — Yjs가 소유. `SlotValue.value.yjs` 에 바이너리로 저장
- **메모** — DB가 소유. `/me` 에서 모아 보려면 질의 가능해야 한다
- **연결** — Yjs 항목이 가진 고유 id 를 `Memo.itemId` 가 참조

### 인증 — 구글 로그인 + admin 승인제

주체는 **서버가 검증한 access token** 에서만 온다. 클라이언트가 `X-User-Id` 로 자칭하던 방식은 걷어냈다 — 그때는 아무나 아무 멤버로 글을 쓸 수 있었다.

- **로그인**: 구글 OAuth2. 성공 핸들러가 refresh 토큰을 httpOnly 쿠키에 심고 프론트를 `/auth/callback` 으로 보낸다. 프론트는 거기서 `POST /api/auth/refresh` 를 한 번 불러 access token 을 받는다 — 그래서 "최초 로그인" 과 "새로고침 자동 로그인" 이 같은 경로다.
- **토큰**: access 는 30분, 메모리(모듈 변수)에만. refresh 는 30일, 불투명 랜덤 문자열이고 DB 에는 SHA-256 해시만 둔다. 갱신할 때마다 회전한다(사용자당 한 행).
- **가입**: 등록 안 된 구글 계정은 거부하지 않고 `access_requests` 에 신청으로 쌓는다. admin(`pj0642@gmail.com`)이 `/admin/members` 에서 승인하면 `PROFILE_REQUIRED`가 되고, 신청자가 다음 구글 로그인에서 이름·색을 직접 입력할 때 `User`가 만들어지며 `APPROVED`가 된다. 승인 전에는 로그인 화면에서 "승인 대기" 안내를 본다.
- **멤버 데이터**: 목 사용자는 만들지 않는다. 실제 멤버는 가입 정보 입력을 완료할 때 생성되고, 스터디에 배정된 멤버와 admin만 멤버별 평점에 노출된다.
- **실시간 서버**: 인증된 REST 요청으로 블록 전용·20초·일회용 티켓을 먼저 발급한다. 접속 URL에는 일반 access token 대신 이 티켓만 넣고, 릴레이가 백엔드 `POST /internal/blocks/{id}/realtime-ticket/consume` 에서 원자적으로 한 번 소비한 뒤 방을 연다. 소켓은 토큰보다 오래 살 수 있으므로 릴레이가 1분마다 `GET /internal/blocks/{id}/access?userId=` 로 다시 물어보고, 거부되거나 스터디에서 빠졌으면 그 자리에서 끊는다. `/internal` 하위는 공유 시크릿 헤더(`X-Internal-Secret`)로 막혀 있다.
- **거부된 계정**: 거부해도 스터디 멤버십은 남으므로 소속만 보면 통과한다. 그래서 REST 는 `JwtAuthenticationFilter`, 실시간은 티켓 발급·소비·재인가 세 지점 모두 `AccessRequestService.canLogin` 을 같이 본다.
- 프론트는 여전히 `useCurrentUser()` 훅 하나로 감싸져 있다.

설정은 `mirelab-backend/application-secret.properties.example` 참고.

### 작품 상태

작품(Work)은 상태를 하나 갖는다. 작품 화면이 이 상태로 갈린다.

| 상태    | 뜻                                      |
| ------- | --------------------------------------- |
| 후보    | 읽고 싶어서 올려둔 것. 아직 모임이 없다 |
| 읽는 중 | 모임이 진행 중                          |
| 완료    | 별점이 확정된 것                        |

작품 화면은 세 상태를 나란히 보여준다. 명예의 전당은 완료 작품만 모아 별점순·최근순으로
탐색하며 스터디의 첫 화면 역할을 한다.

모임이나 별점이 하나라도 걸린 작품은 목록에서 뺄 수 없다 — 기록이 딸려 날아간다.
칸 삭제를 숨김으로 처리한 것과 같은 이유다.

### 프론트 구조의 핵심

칸 타입마다 렌더러를 하나씩 두고 타입으로 찾아 쓴다. 모임 화면은 칸 목록을 받아 순서대로 뿌리기만 한다.

```
RENDERERS = {
  RATING:     별 다섯 개
  TEXT_SHORT: 한 줄 입력
  TEXT_LONG:  textarea
  LIST:       목록 + 추가
  SHARED:     항목 목록 (Yjs) + 메모
}
```

**새 칸 타입 추가 = 렌더러 하나 추가.** 경제 스터디용 타입을 붙일 때도 이 구조가 그대로 간다.

### 속도가 곧 기능

개인 정리를 여기서 하려면 쓰기가 답답한 순간 노션으로 돌아간다. 노션을 떠나는 이유가 버벅임이었다는 걸 잊지 말 것.

- 자동 저장 (제출 버튼을 기다리지 않는다)
- 낙관적 업데이트 — 스피너를 보여주지 않는다
- 모바일은 확인 + 짧은 입력까지. 긴 글과 실시간은 데스크톱

## 5. 기술 결정

### 노션식 블록 에디터는 만들지 않는다

Tiptap/ProseMirror 불필요. `긴 글` 칸은 그냥 textarea. `/` 명령어도, 블록 드래그도, 마크다운 파싱도 없다. **프로젝트 규모가 절반으로 줄어든다.**

애초에 노션의 자유로운 블록이 위 2번 문제(별점을 두 번 쓰는 것)를 만든 원인이라 버리는 게 맞다.

### 실시간 공동 편집 — Yjs

직접 구현하지 않는다. CRDT라 충돌 해결이 수학적으로 보장된다.

서버는 CRDT를 이해할 필요가 없다. Yjs 업데이트는 불투명한 바이트 덩어리고 순서가 뒤바뀌어도 결과가 같으므로, **Spring은 받아서 뿌리고 저장만 한다.**

```
브라우저 A ─┐                          ┌─ 바이너리 그대로 중계
브라우저 B ─┼─ WebSocket ─ Spring ─────┤
브라우저 C ─┘                          └─ DB에 통째로 저장
```

실시간은 **공동 칸에만** 붙는다. 개인 칸은 그냥 저장이라 범위가 작다.

### 외부 API

- **책** — 알라딘 OpenAPI (국내 커버리지 최고, ISBN·표지·목차)
- **영화** — TMDB (포스터, 한국어 지원)

표지 이미지는 등록 시점에 받아서 우리 쪽에 보관한다. 외부 URL을 그대로 쓰면 나중에 깨진다.

`Work.description`(줄거리)과 `Work.actors`(영화 등장 배우)는 이 연동이 붙기 전까지는 자리만
잡아둔다 — 지금은 빈 값이고, 알라딘·TMDB 응답을 그대로 채워 넣을 자리다.

### 프론트 스택

Vite 8 · React 19 · TypeScript · React Router · TanStack Query · Tailwind v4 · oxlint + Prettier

- `/api` → `localhost:8080` dev 프록시. 브라우저 기준 same-origin이라 **백엔드 CORS 설정 불필요**
- `@/` → `src/`
- API는 `src/lib/api.ts` 의 fetch 래퍼. 실패 시 `ApiError(status, body)`
- `queryClient` 는 4xx 재시도 안 함, 5xx만 2회

⚠️ `erasableSyntaxOnly` 가 켜져 있어 **enum과 생성자 파라미터 프로퍼티를 못 쓴다.** enum 대신 `as const` 객체 + 유니온 타입.

### 백엔드 스택

Kotlin 2.3 · Spring Boot 4.1 · JPA · Postgres (dev/prod 공통, Docker Compose로 띄운다 — 테스트만 H2)

## 7. 미결

1. **초안 공개가 자동인가 수동인가** — 자동이면 깜빡해도 공유되고, 수동이면 "아직 안 다듬었는데" 부담이 없다. 둘 다 두면 규칙이 흐려지니 하나만 고른다
2. **메모 달린 항목이 지워지면** — 모임 중 항목을 정리하다 지우는 일이 생긴다. 메모도 사라질지, 인용을 굳혀 내 기록에 남길지
3. **메모 기본값이 공개인가 비공개인가** — 공개가 기본이면 대화가 늘고, 비공개가 기본이면 솔직해진다
4. **리마인더 채널** — 메일이 제일 쉽고, 디스코드 웹훅이면 하루면 붙는다. 카톡 알림톡은 사업자 등록 필요

전부 컬럼 값이나 화면 동작 수준이라 구조를 뒤집지 않는다. 만들면서 정해도 된다.
